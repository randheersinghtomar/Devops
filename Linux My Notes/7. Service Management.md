## <ins> 1. Systemd</ins>


## 1. systemd — The Manager


`systemd` is the **system and service manager** in Linux. Think of it as the manager of your Linux system.

It is the first process started by the kernel during boot and has **PID 1**.

When your EC2 instance starts, `systemd` helps start the services that Linux needs. It manages system services, daemons, startup processes, and system targets. It can also stop services, restart them, and check their status.

For example, if you want to manage Nginx, you use the `systemctl` command, which communicates with `systemd`.

```bash
sudo systemctl start nginx
````

This command tells `systemd` to start the Nginx service.

### Check systemd


Use the following command to check which process is running with PID 1:

Bash

```
ps -p 1 -o comm=
```

Output:

```
systemd
```

### Common systemctl Commands

| Command | Description |
|---|---|
| `systemctl status` | Check the overall system status |
| `systemctl list-units` | List active units |
| `systemctl list-unit-files` | List installed unit files |
| `systemctl get-default` | Check the default target |
| `sudo systemctl reboot` | Reboot the system |
| `sudo systemctl poweroff` | Shut down the system |


### Difference Between systemd and systemctl

| systemd | systemctl |
|---|---|
| The actual system and service manager running in the background. | The command used to manage systemd and its services. |
| It manages services, daemons, and the boot process. | It allows us to start, stop, restart, and check the status of services. |
| It runs as PID 1. | It is a command-line utility used by the administrator. |


### Easy Way to Remember

Think of a hotel:

* systemd = The hotel manager who manages the hotel.

* systemctl = The way you give instructions to the manager.

Similarly, `systemd` manages your Linux system, and `systemctl` is the command you use to give it instructions.


## <ins> 2. Services & Daemons</ins>

A **service** is a program managed by the system that performs a specific task.

A **daemon** is a background process that usually runs without direct user interaction.

Think of it this way:

- **systemd** = The manager
- **Services/Daemons** = The workers doing the actual jobs

For example:

- `nginx` → Web server that serves web pages.
- `sshd` → Handles SSH connections and allows remote access.
- `cron` → Schedules recurring tasks.
- `amazon-ssm-agent` → Enables AWS Systems Manager functionality.

In Ubuntu, services are commonly managed using `systemctl`, which communicates with `systemd`.

### Example

```text
              systemd
            The Manager
                 |
        -------------------
        |        |        |
      nginx     sshd     cron
    Web Server  SSH     Scheduler
````

### Check Service Status

To check whether Nginx is running:

```bash
systemctl status nginx
```

Common status values:

* `active (running)` → Service is running.
* `inactive (dead)` → Service is not running.
* `failed` → Service failed to start or encountered a failure.
* `activating` → Service is in the process of starting.

### Common Service Management Commands

| Command                             | Description                                               |
| ----------------------------------- | --------------------------------------------------------- |
| `sudo systemctl start nginx`        | Start the service now                                     |
| `sudo systemctl stop nginx`         | Stop the service                                          |
| `sudo systemctl restart nginx`      | Stop and start the service again                          |
| `sudo systemctl reload nginx`       | Reload configuration without a full restart, if supported |
| `sudo systemctl status nginx`       | Check service status                                      |
| `sudo systemctl enable nginx`       | Start the service automatically at boot                   |
| `sudo systemctl disable nginx`      | Prevent automatic startup at boot                         |
| `sudo systemctl enable --now nginx` | Enable and start the service                              |
| `sudo systemctl is-active nginx`    | Check whether the service is active                       |
| `sudo systemctl is-enabled nginx`   | Check whether the service is enabled                      |

### Important Differences

* `start` → Starts the service **now**.
* `enable` → Configures the service to start **automatically during boot**.
* `restart` → Stops and starts the service again.
* `reload` → Reloads the configuration without fully restarting the service, if supported.

### List Running Services

To see currently running services:

```bash
systemctl list-units --type=service --state=running
```

### List Installed Service Unit Files

To see all installed service unit files:

```bash
systemctl list-unit-files --type=service
```

### Easy Way to Remember

**systemd = Manager**

**Services/Daemons = Workers**

**systemctl = Command used to give instructions to the manager**

For example:

```bash
sudo systemctl start nginx
```

Here, `systemctl` tells `systemd` to start the `nginx` service.




## <ins> 3. Targets</ins>

## 3. Targets — The System's Operating State

A **target** in `systemd` represents a particular **operating state or mode** of the Linux system.

Think of a target as telling `systemd` **which group of services and system functions should be active**.

Targets are similar to **runlevels** in traditional Linux systems.

### Common systemd Targets

| Target | Easy Meaning |
|---|---|
| `poweroff.target` | Shuts down the system |
| `rescue.target` | Minimal mode used for troubleshooting and maintenance |
| `multi-user.target` | Normal multi-user server mode without a graphical desktop |
| `graphical.target` | Multi-user mode with a graphical desktop |
| `reboot.target` | Reboots the system |

### AWS Example

Since an Ubuntu EC2 instance is normally a **server** and does not need a graphical desktop, it commonly uses:

```text
multi-user.target
````

You can check the default target with:

```bash
systemctl get-default
```

### Target Management Commands

**Check the default target:**

```bash
systemctl get-default
```

**Change the default target:**

```bash
sudo systemctl set-default multi-user.target
```

This changes the target that will be used **after the next boot**.

**Switch to a target immediately:**

```bash
sudo systemctl isolate multi-user.target
```

This changes the system to the specified target **immediately**. It may stop services that are not required by that target.

**Set graphical mode as the default:**

```bash
sudo systemctl set-default graphical.target
```

### Important Difference

| Command       | Meaning                                                 |
| ------------- | ------------------------------------------------------- |
| `set-default` | Changes the default target used at the next boot        |
| `isolate`     | Switches the system to the specified target immediately |

### Easy Way to Remember

**Target = Linux operating mode**

For example:

* `multi-user.target` → Normal server mode
* `graphical.target` → Desktop/GUI mode
* `rescue.target` → Troubleshooting mode
* `poweroff.target` → Shutdown
* `reboot.target` → Reboot


## <ins> 4. Runlevels</ins>


Runlevels are the traditional way of defining the operating state of a Linux system, mainly used by SysVinit.

In systemd-based Linux distributions, runlevels are replaced by targets.

### Traditional runlevels

| Runlevel | Description                              | systemd equivalent  |
| -------- | ---------------------------------------- | ------------------- |
| `0`      | Halt / shutdown                          | `poweroff.target`   |
| `1`      | Single-user / rescue mode                | `rescue.target`     |
| `2`      | Multi-user mode (varies by distribution) | `multi-user.target` |
| `3`      | Multi-user, command-line mode            | `multi-user.target` |
| `4`      | Unused / user-defined                    | No exact equivalent |
| `5`      | Graphical mode                           | `graphical.target`  |
| `6`      | Reboot                                   | `reboot.target`     |

### Check the current runlevel

```
runlevel
```

### Check the default systemd target

```
systemctl get-default
```

**Note:** Runlevels 2, 3, and 4 can have different meanings depending on the Linux distribution. The table shows common traditional mappings.

## <ins>  5. Journald</ins>


`journald` is the logging service provided by systemd. It collects and stores logs from the kernel, system services, and applications.

Logs are accessed using the `journalctl` command.

### Common journalctl commands

| Command                           | Description                                    |
| --------------------------------- | ---------------------------------------------- |
| `journalctl`                      | Display system logs                            |
| `journalctl -b`                   | Show logs from the current boot                |
| `journalctl -b -1`                | Show logs from the previous boot               |
| `journalctl -u nginx`             | Show logs for the Nginx service                |
| `journalctl -u nginx -b`          | Show Nginx logs from the current boot          |
| `journalctl -f`                   | Follow logs in real time                       |
| `journalctl -n 50`                | Show the latest 50 log entries                 |
| `journalctl -p err`               | Show error-level logs and more severe messages |
| `journalctl --since today`        | Show logs since the start of today             |
| `journalctl --since "1 hour ago"` | Show logs from the last hour                   |

### Troubleshooting example

If Nginx fails to start, first check its status:

```
sudo systemctl status nginx
```

Then check its logs:

```
sudo journalctl -u nginx -n 50
```

To follow the logs live:

```
sudo journalctl -u nginx -f
```

### Journald log storage

Journald logs may be stored in volatile or persistent storage, depending on the system configuration.

* `/run/log/journal/` – Volatile logs, generally lost after reboot.

* `/var/log/journal/` – Persistent logs, retained across reboots.

## 6. The Difference You Should Remember


| Term | Description |
|---|---|
| `systemd` | The actual system and service manager running in the background. |
| `systemctl` | The command you use to manage systemd and its services. |
| Service | The application or background process being managed, such as Nginx or SSH. |

### Example

```bash
sudo systemctl start nginx
````

* `systemd` – The actual manager running in the background.

* `systemctl` – The command used to manage services.

* `start` – The action to perform.

* `nginx` – The service being managed.
