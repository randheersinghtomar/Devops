# 1. S3 Basics

## 1.1 Introduction to Amazon S3

**Amazon S3 (Simple Storage Service)** is an AWS service used to **store and retrieve data as objects**.

### Key Features

- **Object storage** – stores files as objects.
- **Highly durable** – designed for **99.999999999% (11 9's) durability**.
- **Scalable** – can store a very large amount of data.
- **Accessible** through AWS Console, CLI, APIs, etc.
- Supports **versioning, encryption, lifecycle policies, replication**, etc.

### Common Use Cases

- Backup and restore
- Storing application files
- Log storage
- Static website hosting
- Data lakes
- Disaster recovery

### Interview Answer

> Amazon S3 is an object storage service provided by AWS. It stores data as objects inside buckets. We commonly use S3 for backups, logs, images, documents, static files and archival data. S3 provides high durability and scalable storage.
---

## 1.2 S3 Bucket & Object

Think of an S3 **Bucket as a container** and an **Object as a file inside that container**.

```text
AWS Account
    |
    └── S3 Bucket
          |
          ├── file1.txt       ← Object
          ├── image.jpg       ← Object
          └── backup.zip      ← Object
````

### Bucket

A **bucket** is a container used to store objects.

* Bucket name must be **globally unique**.
* A bucket is created in a specific **AWS Region**.
* Bucket access can be controlled using policies.

### Object

An **object** is the actual data stored in S3.

An object mainly consists of:

```text
Object
 ├── Data
 ├── Key
 └── Metadata
```

Example:

```text
Bucket: my-company-backup

Object:
my-company-backup/database/backup.sql
```
### Interview Answer

> An S3 bucket is a container where we store objects. An object is the actual data such as images, documents, logs or backup files stored inside the bucket.

---

## 1.3 Object Key, S3 URI & Object URL

### Object Key

The **object key is the complete name/path used to identify an object inside a bucket.**

Object Key — "What is the file called?"

Example:

```text
Bucket: my-bucket

Key: backups/database/backup.sql
```

> S3 does **not actually use folders** like a Linux filesystem. `backups/database/` is part of the object's key.

### S3 URI

Used to identify an S3 object in AWS.

S3 URI — "Where is the file in S3?"

```text
s3://bucket-name/object-key
```

Example:

```text
s3://my-bucket/backups/database/backup.sql
```

### Object URL

Used to access an object through an HTTP/HTTPS URL, depending on the object's permissions.

Example:

```text
https://my-bucket.s3.amazonaws.com/backups/database/backup.sql
```
Key points:- 
Having an Object URL does **not** mean that the object is publicly accessible.
If public access is blocked and the user does not have permission, accessing the Object URL can return:

```text
Access Denied
```

### Easy Difference

Imagine a **hotel**:

```text
Hotel       → Bucket
Room number → Object Key
Full address → S3 URI
Door access/link → Object URL

Object Key → backups/database/backup.sql
S3 URI     → s3://my-bucket/backups/database/backup.sql
Object URL → https://my-bucket.s3.amazonaws.com/backups/database/backup.sql
```

## 1.4 Bucket Naming & Regions

### Bucket Naming

S3 bucket names must:

* Be **globally unique** across S3.
* Generally be **3–63 characters** long.
* Use lowercase letters, numbers, hyphens, and periods where allowed.
* Not contain spaces or underscores.

Example:

```text
my-company-backup-2026
```

### S3 Region

A bucket is created in a specific AWS Region.

Example:

```text
S3 Bucket
    |
    └── Region: ap-south-1 (Mumbai)
```

The region affects:

* Data access latency
* Data transfer costs
* Compliance/data residency
* Integration with other AWS services

> **Interview Point:** S3 is a **regional service**, but bucket names are **globally unique**.

# 2. Storage & Object Management

## 2.1 S3 Storage Classes

**S3 Storage Classes** are different options for storing data based on **how often you access it and how much you want to pay**.

S3 provides different storage classes based on:

- Access frequency
- Retrieval requirement
- Availability requirement
- Storage cost
- Archival requirement

Think of them like different types of storage rooms:

```text
Frequently accessed
        ↓
   S3 Standard
        ↓
Less frequently accessed
        ↓
   Standard-IA
        ↓
Rarely accessed
        ↓
      Glacier
        ↓
Almost never accessed
        ↓
  Glacier Deep Archive
````

### Important Storage Classes

| Storage Class                     | Best For                                         |
| --------------------------------- | ------------------------------------------------ |
| **S3 Standard**                   | Frequently accessed data                         |
| **S3 Intelligent-Tiering**        | Data with changing/unknown access patterns       |
| **S3 Standard-IA**                | Data accessed less frequently                    |
| **S3 One Zone-IA**                | Infrequently accessed data that can be recreated |
| **S3 Glacier Instant Retrieval**  | Archive data that needs quick access             |
| **S3 Glacier Flexible Retrieval** | Long-term archive data                           |
| **S3 Glacier Deep Archive**       | Very rarely accessed, long-term archive          |



### 6.1 S3 Standard— "I use it regularly"

Used for **frequently accessed data**.

Features:

- Multi-AZ
- High availability
- Millisecond access
- 99.999999999% (11 9s) durability
- Suitable for frequently accessed objects

Examples:

- Active application files
- Frequently accessed documents
- Images
- Website content

#### Interview Answer

> S3 Standard is used for frequently accessed data. It provides high availability, Multi-AZ storage and 11 9s durability.

### 6.2 S3 Intelligent-Tiering— "I don't know how often I'll use it"

Used when the access pattern of data is **unknown or changes over time**.

S3 monitors access patterns and automatically moves objects between appropriate access tiers to optimize storage cost.

Features:

- Automatic cost optimization
- Useful when access pattern is unpredictable
- Monitoring and automation charges apply

#### Interview Answer

> S3 Intelligent-Tiering is useful when we don't know how frequently data will be accessed. AWS automatically moves objects between access tiers based on usage to optimize storage cost.

### 6.3 S3 Standard-IA— "I rarely use it, but when I need it, I need it immediately"

IA stands for **Infrequent Access**.

Used when data is accessed infrequently but must be available immediately when required.

Features:

- Multi-AZ
- Millisecond retrieval
- Lower storage cost than S3 Standard
- Retrieval charges apply
- Minimum storage duration: 30 days

Examples:

- Backups
- Disaster recovery files
- Infrequently accessed business data

#### Interview Answer

> S3 Standard-IA is used for data that is accessed infrequently but needs immediate retrieval when required. Storage cost is lower than S3 Standard, but retrieval charges apply.

### 6.4 S3 One Zone-IA— "I rarely use it and I can recreate it"

Used for infrequently accessed data stored in a **single Availability Zone**.

Features:

- Single AZ
- Immediate retrieval
- Lower cost than Standard-IA
- Retrieval charges apply
- Minimum storage duration: 30 days
- Suitable for re-creatable data

Because the data is stored in one AZ, it should not normally be used as the only copy of critical data.

Recreate = "If I lose this file, I can make the same data again from another source."

#### Interview Answer

> S3 One Zone-IA is used for infrequently accessed and re-creatable data. It stores data in a single Availability Zone and costs less than Standard-IA.

---

## 7. S3 Glacier Storage Classes

Glacier storage classes are mainly used for **archive data**.


### 7.1 Glacier Instant Retrieval

Used for archive data that is rarely accessed but needs **millisecond retrieval** when required.

```text
Archive Data
+
Rarely Accessed
+
Millisecond Retrieval
```

### 7.2 Glacier Flexible Retrieval

Used for archive data where immediate retrieval is not required.

Retrieval can range from **minutes to hours**, depending on the retrieval option.

```text
Archive Data
+
Rarely Accessed
+
Minutes/Hours Retrieval
```

### 7.3 Glacier Deep Archive

Used for **long-term archival data** that is very rarely accessed.

Examples:

- Long-term compliance records
- Old financial records
- Historical backups
- Long-term company records

Retrieval normally takes hours.

```text
Long-Term Archive
+
Very Rare Access
+
Hours Retrieval
+
Very Low Storage Cost
```

#### Easy Interview Point

> **S3 Standard = frequently used data, IA = occasionally used data, Glacier = archive data.**

# 2.2 Upload, Download, Copy & Delete

S3 allows us to perform basic operations on objects.

```text
Bucket
  |
  ├── Upload    → Put file into S3
  ├── Download  → Get file from S3
  ├── Copy      → Make a copy of an object
  └── Delete    → Remove an object
```

### Upload

Putting a file into an S3 bucket.

```text
Laptop → S3 Bucket
```

Example:

```bash
aws s3 cp backup.zip s3://my-bucket/
```

### Download

Getting an object from S3 to your system.

```text
S3 Bucket → Laptop
```

```bash
aws s3 cp s3://my-bucket/backup.zip .
```

### Copy

Copying an object from one S3 location to another.

```text
Bucket A → Bucket B
```

```bash
aws s3 cp s3://bucket-a/file.txt s3://bucket-b/
```

### Delete

Removing an object from a bucket.

```bash
aws s3 rm s3://my-bucket/file.txt
```

> **Important:** If **Versioning is enabled**, deleting an object normally creates a **Delete Marker** instead of immediately permanently removing all versions.

# 2.3 Multipart Upload

**Multipart Upload** means breaking a large file into **smaller parts** and uploading those parts separately.

Instead of:

```text
10 GB File
    |
    ↓
Single Upload
```

S3 can do:

```text
10 GB File
    |
    ├── Part 1
    ├── Part 2
    ├── Part 3
    ├── Part 4
    └── ...
          ↓
       S3 Bucket
          ↓
    S3 combines parts
```

### Why use it?

* Better for **large files**
* Multipart upload is recommended for objects larger than 5 GB.
* Parts can be uploaded **in parallel**
* If one part fails, we can retry **only that part**
* Improves upload performance

> **Interview Point:** Multipart Upload is especially useful for large objects and unreliable network connections.

# 2.4 Object Metadata & Tags

## Object Metadata

**Metadata is information about the object.**

Think:

> **File = actual data**
> **Metadata = information about the file**

Example:

```text
Object: backup.zip

Metadata:
├── Content-Type
├── Size
├── Last Modified
└── Encryption information
```

Some metadata is automatically created by S3, while some can be provided by the user/application.

## Object Tags

**Tags are key-value labels attached to an S3 object.**

Example:

```text
Object: backup.zip

Tags:
Environment = Production
Department  = Finance
Backup      = Daily
```

Tags are useful for:

* Organizing objects
* Lifecycle rules
* Cost management
* Identifying data
* Automation

### Metadata vs Tags

```text
Metadata → Information/details about the object

Tags     → Labels we attach to the object
```

### Easy Example

Imagine a **parcel**:

```text
Parcel
  |
  ├── Actual item     → Object
  ├── Parcel details  → Metadata
  └── Labels          → Tags
```

Multipart upload breaks large files into smaller parts for efficient and reliable uploads. Metadata provides information about an object, while tags are key-value labels used for organization and management."

# 3. S3 Versioning & Lifecycle

## 3.1) S3 Versioning

**S3 Versioning** keeps multiple versions of the same object in a bucket.

Without Versioning:

```text
data.txt
   ↓
Upload new data.txt
   ↓
Old file is replaced
````

With Versioning:

```text
data.txt
   |
   ├── Version 1 → Old content
   ├── Version 2 → Updated content
   └── Version 3 → Latest content
```

### Why use Versioning?

* Protects against accidental deletion
* Protects against accidental overwriting
* Allows recovery of previous versions
* Useful for data protection and backup

> **Important:** Versioning must be enabled on the bucket.

## Versioning Hands-on

The following practical was completed:

### Step 1

Created S3 bucket:

```text
Randheer-s3-practice-2026
```

### Step 2

Uploaded:

```text
Docker.docx
```

### Step 3

Enabled S3 Versioning.

### Step 4

Uploaded the same object again.

Verified multiple versions:

```text
Docker.docx → New Version ID
Docker.docx → Previous Version
```

The original object uploaded before enabling Versioning had:

```text
Version ID = null
```

### Step 5

Deleted the current object.

Verified:

```text
Delete Marker
```

was created.

### Step 6

Previous object versions remained available.

### Step 7

Deleted the Delete Marker.

The previous latest version became visible again.

### Practical Result

```text
Versioning Enabled
        ↓
Same Object Uploaded
        ↓
Multiple Versions Created
        ↓
Object Deleted
        ↓
Delete Marker Created
        ↓
Delete Marker Removed
        ↓
Object Restored
```

## 3.2) Version ID & Delete Marker

### Version ID

Every version of an object gets a **unique Version ID**.

Example:

```text
data.txt

Version ID: abc123 → Old version
Version ID: xyz789 → New version
```

The latest version is normally returned when you request the object without specifying a Version ID.

### Delete Marker

When **Versioning is enabled**, deleting an object does not immediately remove the previous version.

Instead, S3 creates a **Delete Marker**.

```text
data.txt
   |
   ├── Version 1 → File
   ├── Version 2 → File
   └── Delete Marker
```

To the normal user, the object appears deleted.

But the previous versions still exist.

> **Simple meaning:** Delete Marker = Makes the object look deleted while keeping previous versions.

## 3.3) Object Recovery

Versioning allows you to recover accidentally deleted or overwritten objects.

### Accidental Deletion

Before deletion:

```text
data.txt
   ↓
Version 1
```

After deletion:

```text
data.txt
   ↓
Delete Marker
```

The old version still exists.

To recover the object, remove the **Delete Marker**.

```text
Delete Marker ❌
Version 1      ✅
       ↓
data.txt is recovered
```

### Accidental Overwrite

If you accidentally upload incorrect content:

```text
Version 1 → Correct file
Version 2 → Wrong file
```

You can retrieve the previous version.


# 3.4) Lifecycle Policy

**S3 Lifecycle** automatically manages objects based on their age.

Lifecycle Policy Example: 

Suppose application logs are uploaded to S3.

Requirement:

```text
Day 1 - 30
S3 Standard

Day 31 - 90
Standard-IA

Day 91 - 180
Glacier Flexible Retrieval

Day 181+
Glacier Deep Archive

Then Delete ( If required)
```

Lifecycle configuration:

```text
30 Days  → Standard-IA
90 Days  → Glacier Flexible
180 Days → Glacier Deep Archive
Delete
```

Important:

The number of days refers to the **age of the object from its creation/upload**, not the number of days spent in the previous storage class.



### Lifecycle Transition

A **Transition** means moving an object from one S3 storage class to another.

Example:

```text
S3 Standard
     ↓ 30 days
S3 Standard-IA
     ↓ 60 days
S3 Glacier
```

This can reduce storage costs for older or rarely accessed data.

### Example

> Move objects from S3 Standard to S3 Glacier after 90 days.

S3 automatically performs the transition according to the lifecycle rule.


### Object Expiration

**Expiration** means S3 automatically deletes objects after a specified period.

Example:

```text
Object uploaded
      ↓
180 days
      ↓
Object expires
      ↓
Deleted
```

### Example

For temporary application logs:

```text
logs/
   ↓
Keep for 30 days
   ↓
Automatically delete
```

You can create a lifecycle rule:

> Delete objects under `logs/` after 30 days.


# 3.5) Lifecycle with Versioning

Versioning can create multiple old versions of objects.

These old versions consume storage.

Lifecycle rules can manage:

- Current object versions
- Noncurrent object versions
- Delete markers
- Incomplete multipart uploads

For example:

```text
Old Version
    ↓
Transition to cheaper storage
    ↓
Expire after retention period
```

This helps reduce unnecessary S3 storage cost.

# 4. S3 Security

S3 Security is mainly about:

- **Who can access the bucket/objects**
- **Whether the bucket is publicly accessible**
- **How data is protected using encryption**


## 4.1) IAM Policy vs Bucket Policy

Both are used to control access to S3.

### IAM Policy

An **IAM Policy** is attached to:

- IAM User
- IAM Group
- IAM Role

```text
IAM User / Role
       |
       ↓
 IAM Policy
       |
       ↓
  S3 Bucket
````

Example:

> Allow this EC2 IAM Role to read objects from an S3 bucket.

### Bucket Policy

A **Bucket Policy** is attached directly to the **S3 Bucket**.

```text
S3 Bucket
    |
    ↓
Bucket Policy
    |
    ↓
Who can access the bucket?
```

Example:

> Allow a role from another AWS account to access this bucket.

### Main Difference

| IAM Policy                       | Bucket Policy                                    |
| -------------------------------- | ------------------------------------------------ |
| Attached to User, Group, or Role | Attached to S3 Bucket                            |
| Defines what the identity can do | Defines who can access the bucket                |
| Common for users/roles           | Useful for bucket-level and cross-account access |

### Easy Way to Remember

```text
IAM Policy
→ What can this User/Role do?

Bucket Policy
→ Who can access this Bucket?
```


## 4.2) Block Public Access

**S3 Block Public Access** helps prevent your S3 bucket and objects from being accidentally exposed to the public.

Without protection:

```text
Internet
   ↓
S3 Bucket
   ↓
Anyone can access ❌
```

With Block Public Access:

```text
Internet
   ↓
S3 Bucket
   ↓
Public access blocked ❌
```

AWS provides **four Block Public Access settings** that prevent different ways of making S3 resources public.

### Important

For a normal private S3 bucket:

```text
Block Public Access = ON
```

> **Interview Point:** Block Public Access helps prevent accidental public exposure. It does not replace IAM or Bucket Policies.


## 4.3) ACL & Object Ownership

### ACL — Access Control List

An **ACL** is an older S3 mechanism for controlling access to buckets and objects.

It can define permissions such as:

```text
Read
Write
Read ACL
Write ACL
```

Example:

```text
Object
  |
  ↓
 ACL
  |
  ├── Account A → Read
  └── Account B → Read/Write
```

Modern S3 applications generally prefer **IAM Policies and Bucket Policies** instead of ACLs.


### Object Ownership

**Object Ownership** determines who owns objects uploaded to an S3 bucket.

The commonly recommended setting is:

```text
Bucket owner enforced
```

With this setting:

```text
User A uploads object
        ↓
     S3 Bucket
        ↓
Bucket owner owns object
```

ACLs are disabled.

### Why is this useful?

It simplifies permissions because you don't need to manage object ownership between different AWS accounts.

### Easy Way to Remember

```text
ACL
→ Older way of managing object permissions

Object Ownership
→ Determines who owns uploaded objects

Bucket owner enforced
→ Bucket owner owns objects
→ ACLs are disabled
```


## 4.4) S3 Encryption (SSE-S3, SSE-KMS, SSE-C)

Encryption protects your data **at rest**.

```text
Before Encryption
      ↓
  Hello AWS
      ↓
Stored as readable data


After Encryption
      ↓
  Hello AWS
      ↓
Encrypted data
```

There are three important server-side encryption options:


### SSE-S3

**SSE-S3 = Server-Side Encryption with S3-managed keys**

S3 manages the encryption keys for you.

```text
Your Object
    ↓
   S3
    ↓
Encryption
    ↓
S3-managed key
```

#### Simple Meaning

> S3 manages the encryption keys.


### SSE-KMS

**SSE-KMS = Server-Side Encryption with AWS KMS keys**

S3 uses keys managed through **AWS KMS**.

```text
Your Object
    ↓
   S3
    ↓
 AWS KMS
    ↓
 KMS Key
```

Advantages:

* More control over encryption keys
* IAM/KMS policies can control key access
* Key usage can be audited
* Useful for stricter security requirements

#### Simple Meaning

> KMS gives you more control over the encryption key.


### SSE-C

**SSE-C = Server-Side Encryption with Customer-provided keys**

You provide the encryption key to S3.

```text
You
 ↓
Encryption Key
 ↓
 S3
 ↓
Encrypts Object
```

AWS performs the encryption/decryption, but **you provide and manage the key**.

#### Simple Meaning

> Customer provides the encryption key.

---

### Encryption Quick Comparison

| Type        | Who manages the key? |
| ----------- | -------------------- |
| **SSE-S3**  | AWS/S3               |
| **SSE-KMS** | AWS KMS              |
| **SSE-C**   | Customer             |

### Easy Way to Remember

```text
SSE-S3 → S3 manages key
SSE-KMS → KMS manages key
SSE-C  → Customer provides key
```


## 4.5) Cross-Account Access

Cross-account access means allowing a user or role from **AWS Account B** to access an S3 bucket in **AWS Account A**.

```text
AWS Account A
     |
     ↓
 S3 Bucket
     ↑
     |
AWS Account B
 User / Role
```

Example:

```text
Account A
└── S3 Bucket: company-data

Account B
└── IAM Role: backup-role
```

You can allow `backup-role` from Account B to access the S3 bucket in Account A.

This is commonly done using:

* **Bucket Policy** in Account A
* **IAM Policy** in Account B

```text
Account A
S3 Bucket
   |
   | Bucket Policy
   ↓
Allows Account B Role
   ↑
   |
IAM Policy
Account B Role
```

> **Interview Point:** Cross-account access usually requires permission from both the resource side and the requesting identity side.

### Practical: -

# IAM Cross-Account Access — Assume Role / Switch Role

## Scenario

Suppose we have two AWS accounts:

```text
Account A
   |
   └── IAM User: Amit
          |
          | wants to access
          ↓
Account B
   |
   └── AWS Resources
       (S3, EC2, etc.)
```

### Requirement

Amit is an IAM user in **Account A**.

He needs to temporarily access resources in **Account B**.

Instead of creating another IAM user in Account B, we can use an **IAM Role** and allow Amit to **AssumeRole**.



# Step 1 — Create a Role in Account B

Login to **Account B**.

Go to:

```text
IAM → Roles → Create Role
```

### Trusted Entity

Select:

```text
AWS Account
```

Enter **Account A's Account ID**.

Example:

```text
Account A ID = 111111111111
```

This means:

> Account B trusts Account A to assume this role.

### Role Name

For example:

```text
cross
```

### Attach Permissions

Give the role the permissions Amit needs.

For example, if Amit needs read-only access to S3:

```text
AmazonS3ReadOnlyAccess
```

So Account B has:

```text
Account B
   |
   └── IAM Role: cross
          |
          └── S3 ReadOnly permissions
```



# Step 2 — Copy the Role ARN

After creating the role, copy its **Role ARN**.

Example:

```text
arn:aws:iam::222222222222:role/cross
```

Here:

```text
222222222222 = Account B ID
cross        = Role name
```



# Step 3 — Give Amit AssumeRole Permission

Now go to **Account A**.

Amit needs permission to assume the role in Account B.

The required action is:

```text
sts:AssumeRole
```

Create a policy for Amit:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::222222222222:role/cross"
    }
  ]
}
```

Attach this policy to **Amit**.

This means:

> Amit is allowed to assume the `cross` role in Account B.



# Step 4 — Switch Role

Login to AWS as **Amit** in Account A.

Choose:

```text
Switch Role
```

Enter:

```text
Account ID: 222222222222
Role Name:  cross
```

Then select:

```text
Switch Role
```

Amit is now operating using the permissions of the **`cross` role in Account B**.

The flow is:

```text
Amit
(Account A)
   |
   | sts:AssumeRole
   ↓
cross Role
(Account B)
   |
   | S3 ReadOnly permission
   ↓
S3 Resources
(Account B)
```


# Important Concept

Cross-account access requires permissions on **both sides**.

| Account       | Configuration                                          |
| ------------- | ------------------------------------------------------ |
| **Account A** | Amit is allowed to perform `sts:AssumeRole`            |
| **Account B** | The role trusts Account A                              |
| **Account B** | The role has the actual permissions, such as S3 access |

### Simple way to remember

```text
Account A
   |
   | "Amit can assume the role"
   ↓
Account B
   |
   | "I trust Account A"
   ↓
IAM Role
   |
   | "You can read S3"
   ↓
S3 Resources
```

## Interview Answer

> **Cross-account access allows a user in one AWS account to temporarily access resources in another AWS account by assuming an IAM role. The source account gives the user `sts:AssumeRole` permission, while the destination account's role trusts the source account and contains the permissions required to access the resources.**

# 5. S3 Advanced Features


### 1. S3 Replication — SRR & CRR

**S3 Replication** automatically copies objects from one S3 bucket to another bucket.

#### Why Use Replication?

- Disaster Recovery
- Data redundancy
- Compliance
- Cross-region availability
- Keeping copies of data in another AWS account

#### Types of Replication

| Type | Full Form | Replication |
|---|---|---|
| **SRR** | Same-Region Replication | Bucket → Bucket in same AWS Region |
| **CRR** | Cross-Region Replication | Bucket → Bucket in different AWS Region |

#### CRR Example

```text
Mumbai Region
     |
     | S3 Replication
     ↓
Singapore Region
````

If an object is uploaded to:

```text
my-source-bucket
```

AWS can automatically replicate it to:

```text
my-dr-bucket
```

#### Important Points

* Source and destination buckets need Versioning enabled for live replication.
* Replication is configured using replication rules.
* You can replicate:

  * All objects
  * Objects matching specific prefixes
  * Objects matching specific tags
* Replication can work across AWS accounts.
* Existing objects can be replicated using **S3 Batch Replication**.
* Replication is asynchronous.

#### Interview Question

**Q: What is the difference between SRR and CRR?**

**Answer:**

SRR replicates objects between S3 buckets in the **same AWS Region**, while CRR replicates objects between buckets in **different AWS Regions**.


### 2. Pre-Signed URLs

A **Pre-Signed URL** provides temporary access to an S3 object without making the bucket or object public.

#### Example

Suppose this file is private:

```text
s3://my-bucket/reports/report.pdf
```

The application can generate a pre-signed URL valid for a specific period.

```text

       ↓

Pre-Signed URL
       ↓

       ↓
URL expires
```

#### Use Cases

* Temporary download access
* Temporary upload access
* Sharing private files
* Allowing users to upload directly to S3
* Avoiding the need to give users AWS credentials

#### Important Points

* Pre-signed URLs provide temporary access.
* The URL has an expiration time.
* The permissions are based on the identity that generated the URL.
* They can be used for both **GET (download)** and **PUT (upload)** operations.
* The object itself does not need to be made public.

#### Interview Question

**Q: Why use a pre-signed URL instead of making an S3 object public?**

**Answer:**

A pre-signed URL provides **temporary and controlled access** to a private S3 object without making the object publicly accessible.

### 5. S3 Object Lock

**S3 Object Lock** protects objects from being deleted or overwritten for a defined period.

#### Use Cases

* Compliance
* Regulatory requirements
* Backup protection
* Preventing accidental deletion
* Protection against unwanted modification

#### Example

```text
Backup File
    ↓
S3 Object Lock
    ↓
Cannot be deleted
until retention period expires
```

### Retention Modes

#### Governance Mode

Authorized users with special permissions can bypass the retention settings.

#### Compliance Mode

The protected object cannot be deleted or modified until the retention period expires.

### Legal Hold

A **Legal Hold** can also be placed on an object.

A legal hold prevents deletion until the legal hold is explicitly removed.

### Important Point

S3 Object Lock works with **S3 Versioning**.

### Interview Question

**Q: What is the difference between Governance and Compliance mode?**

**Answer:**

Governance mode allows specially authorized users to bypass retention, while Compliance mode provides stronger protection and does not allow the retention to be bypassed until it expires.

It is useful when multiple applications or teams need different access permissions to the same bucket.

       Finance        HR Users     Developers

#### Benefits

* Simplifies access management
* Separate policies for different applications
* Useful for shared buckets
* Can provide different network controls
* Useful for large-scale S3 environments

#### Interview Question

**Q: Why would you use S3 Access Points?**

**Answer:**

When multiple applications or teams access the same S3 bucket with different permissions, Access Points allow us to create separate access policies and endpoints instead of maintaining one complex bucket policy.

#### 11. Directory Buckets — Basics

* Very low latency
* High request rates
* Fast data access
* High-performance data processing

#### Important Difference

| Feature          | General-Purpose Bucket | Directory Bucket                |
| ---------------- | ---------------------- | ------------------------------- |
| Storage          | General S3 storage     | S3 Express One Zone             |
| Storage location | Regional               | Single AZ                       |

#### Important Interview Point

Directory buckets use **S3 Express One Zone**, where data is stored in a **single Availability Zone**.

Therefore, they are suitable when very low latency is important and the application has an appropriate resilience strategy.

# 16. Day 01 Important Interview Questions

### Q1. What is Amazon S3?

Amazon S3 is an object storage service used to store data as objects inside buckets.

### Q2. What is the difference between a bucket and an object?

A bucket is a container, while an object is the actual data stored inside the bucket.

### Q3. What is an Object Key?

An Object Key uniquely identifies an object inside an S3 bucket.

### Q4. Which storage class is suitable for frequently accessed data?

S3 Standard.

### Q5. Which class is suitable for infrequently accessed data requiring immediate retrieval?

S3 Standard-IA.

### Q6. Standard-IA vs One Zone-IA?

Standard-IA stores data across multiple AZs, while One Zone-IA stores data in a single AZ and costs less.

### Q7. When would you use Intelligent-Tiering?

When the access pattern is unknown or changes over time.

### Q8. What is S3 Versioning?

Versioning maintains multiple versions of the same object and helps recover from accidental overwrite or deletion.

### Q9. What happens when we delete an object from a version-enabled bucket?

S3 normally creates a Delete Marker while previous versions remain available.

### Q10. What is an S3 Lifecycle Policy?

It automatically transitions objects between storage classes or expires them based on configured rules.

### Q11. Why do we use Lifecycle Policies?

To automate data management and optimize S3 storage costs.

# Production Scenario Questions & Answers

## Q1. A user is getting Access Denied while accessing an S3 object. How will you troubleshoot?

Answer:

First I will confirm which IAM user or role is making the request.

Then I will check:

1. IAM policy
2. S3 bucket policy
3. Any explicit Deny
4. Block Public Access if public access is expected
5. KMS permissions if the object uses SSE-KMS
6. Object/bucket path and required S3 action

An explicit Deny overrides an Allow.


## Q2. An important S3 file was accidentally deleted. How will you recover it?

Answer:

I will first check whether S3 Versioning is enabled.

If versioning is enabled, deletion normally creates a delete marker while previous object versions remain available.

I can restore the required previous version or remove the delete marker as appropriate.

---

## Q3. The company wants old S3 data automatically moved to cheaper storage. What will you do?

Answer:

I will configure an S3 Lifecycle Policy.

Example:

Frequently accessed data
→ S3 Standard

After required number of days
→ Standard-IA

Later
→ Glacier storage class

Finally, if required
→ Expire/Delete

This reduces storage cost automatically.

---

## Q4. A private S3 file needs to be shared with an external user for a limited time. What will you do?

Answer:

I will generate a Presigned URL.

This provides temporary access to the private object without making the bucket public.

The URL expires after the configured period.

---

## Q5. The application uploads very large files to S3 and uploads are slow or individual transfers sometimes fail. What will you recommend?

Answer:

I will use Multipart Upload.

Large files are uploaded in multiple parts and parts can be transferred concurrently.

If an individual part fails during the multipart operation, that part can be retried without restarting all successfully uploaded parts within that active transfer.

---

## Q6. Incomplete multipart uploads are increasing S3 storage cost. How will you fix it?

Answer:

I will configure an S3 Lifecycle rule to abort incomplete multipart uploads after a specified number of days.

This automatically cleans up unused multipart parts and helps avoid unnecessary storage cost.

---

## Q7. Users in another country are experiencing slow uploads to an S3 bucket located far away. What can you use?

Answer:

I will evaluate S3 Transfer Acceleration.

It uses nearby AWS edge locations and the AWS global network to improve long-distance data transfer.

Since it has additional cost, I would enable it when the performance benefit justifies it.

---

## Q8. The company requires audit records that must not be deleted for 7 years. What will you use?

Answer:

I will use S3 Object Lock with an appropriate retention period.

For strict regulatory requirements, Compliance Mode can be used.

It follows the WORM model — Write Once, Read Many.

---

## Q9. The company requires an S3 copy in another AWS Region for Disaster Recovery. What will you configure?

Answer:

I will configure S3 Cross-Region Replication (CRR).

Versioning must be enabled on the source and destination buckets.

I will configure the replication rule and required IAM permissions.

---

## Q10. An EC2 instance in Account A needs access to an S3 bucket in Account B without storing access keys on the server. How will you configure it?

Answer:

I will create an IAM role for EC2 in Account A and attach the required S3 permissions.

Then I will attach the role to the EC2 instance.

In Account B, I will configure the S3 bucket policy to allow the ARN of the Account A EC2 role.

Then from EC2 I can access the bucket, for example:

aws s3 ls s3://companydata

No long-term access keys need to be stored on the EC2 instance.

---

## Q11. A static website hosted on S3 is not opening publicly. What will you check?

Answer:

I will check:

1. Static website hosting is enabled.
2. Correct index document such as index.html is configured.
3. Required website files exist.
4. Bucket policy allows required public GetObject access.
5. S3 Block Public Access settings are consistent with the intended public website configuration.
6. Correct S3 website endpoint is being used.

---

## Q12. An S3 bucket uses SSE-KMS and a user has S3 permissions but still gets Access Denied while downloading an object. What will you check?

Answer:

I will check both S3 permissions and KMS permissions.

With SSE-KMS, having S3 GetObject permission alone may not be sufficient.

I will verify:

- IAM permissions
- Bucket policy
- KMS key policy
- Required KMS permissions
- Any explicit Deny

The user/role must be authorised to use the KMS key for the required operation.
